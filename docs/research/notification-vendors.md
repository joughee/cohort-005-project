# Notification vendors vs building our own

Research for the ticket "Notification vendors vs building our own", a child of "Map: In-app and email notifications". Sources were read on 2026-11-12. Pricing pages change often, so check them again before deciding.

This file gives facts and trade-offs only. The build-vs-buy decision belongs to the follow-up grilling ticket.

## Cadence constraints

- React Router 8.3, one Node process, one SQLite file through `better-sqlite3` and Drizzle (ADR 0006). The ADR says the app can't run on more than one machine against the same data.
- Email goes through `app/lib/mailer.server.ts`. It POSTs to Postmark's `/email` endpoint with `TextBody` only and a fixed `MessageStream: "outbound"`. Without `POSTMARK_SERVER_TOKEN` it writes JSON files to `.outbox/`. It can't send custom headers, HTML bodies or other streams yet.
- In-app Notifications only need to update on navigation plus polling. No live push.
- Needs: per-type preferences, an unsubscribe link on engagement Email Notifications, and maybe digests and scheduled sends. Triggers are new Comments for Instructors and Replies for Students, plus engagement nudges.

All vendor feeds are described as real-time over a socket. Knock's only documented control is `auto_manage_socket_connection`, which disconnects idle tabs. A fetch-only or polling mode isn't documented [K9]. Cadence doesn't need live push, so this connection is extra and doesn't add anything we need.

## How each vendor fits a single-process React Router + SQLite app

These points apply to all vendors:

- **Data lives in two places.** The feed, read/unread state and preferences live with the vendor. Our SQLite data (Comments, Replies, enrollments) can't join against them in one query, so the app needs a network call or SDK state. Every recipient must also be identified to the vendor (user ID, email, name), so user data leaves the SQLite file.
- **Triggers become network calls.** Today a loader or action is a synchronous `better-sqlite3` query. With a vendor, a trigger becomes an HTTP request after the write commits, and its failures need handling (retry or log) outside the SQLite transaction.
- **Dev and test move off `.outbox`.** Vendor runs need a dev environment, and every vendor has 2 or more. Tests would mock the vendor client, or the vendor would point at Postmark's sandbox (Knock has a sandbox toggle [K2]). The current `.outbox/` JSON pattern wouldn't see vendor-sent email.
- **You get scheduling, digests and preferences without running a scheduler yourself.** A single-process app otherwise has to own those (see below).
- **Vendor-specific notes:**
  - Knock covers every listed need (feed, Postmark, preferences, commercial unsubscribe, batch, delay plus cancel, schedules) on the free tier, but jumps from free to $250/mo.
  - Novu is the only one you can self-host, but its stack (Mongo, Redis, workers) is far heavier than Cadence's one-process, one-file design. Its free tier caps digest windows at 1 day and workflows at 5.
  - MagicBell doesn't list Postmark as a provider. It might work through its generic SMTP provider, since Postmark offers SMTP, but that wasn't checked.
  - Courier Business bills every send from the first one, and its pricing page lists digests under Enterprise.

What counts as one billable unit (a trigger, or each channel's delivery) differs between vendors and wasn't checked closely. Knock bills "messages sent", Novu "workflow runs", MagicBell "deliveries" and Courier "sends". One event that produces both an In-app Notification and an Email Notification may count once or twice depending on the vendor.

## What a home-built version would need

Built on SQLite, Drizzle, the existing mailer and React Router:

1. **Schema** (see the `database-migrations` skill):
   - An `in_app_notifications` table: recipient user ID (any user, which leaves room for Platform Admin notifications later), a `type` from an extensible enum, a subject reference (Comment or Reply ID), `created_at` and `read_at`.
   - A per-user, per-type, per-channel preferences table with code-defined defaults.
   - Possibly an `email_notifications` log, for idempotency and to collect items for digests.
2. **Fan-out at trigger time.** Inside the action that creates the Comment or Reply, insert the In-app Notification rows in the same synchronous SQLite transaction. Check preferences, then send the Email Notification after the commit.
3. **Feed UI.** A root or layout loader returns the unread count, so it refreshes on every navigation. Polling uses React Router's `useRevalidator` or a `useFetcher` on an interval against a resource route. Mark-read is an action. No socket is needed.
4. **Mailer extensions.** `Email` needs optional `HtmlBody`, `Headers` and `MessageStream` fields. The `.outbox` transport should record them so tests can assert on them.
5. **Unsubscribe.**
   - Postmark requires an unsubscribe link on Broadcast streams and makes it optional on Transactional ones [P1].
   - On a Broadcast stream, Postmark adds a one-click link (`{{{ pm:unsubscribe }}}`) and the RFC 8058 headers automatically. Suppressions are per stream, and the Subscription Change webhook or suppressions API can sync them back to our preferences table [P1][P2].
   - Alternatively, we send our own `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers, which Postmark passes through on Transactional streams. That needs a signed-token route that accepts a POST and updates the preference [P2].
   - Postmark describes Transactional as one recipient, triggered by a user action (its example is comment notifications), and Broadcast as many recipients at once [P3]. Where engagement nudges belong is a judgement call.
6. **Scheduler (for digests, delays and engagement nudges).**
   - Because there is one process, an in-process timer (`setInterval` or a cron library) can poll a `scheduled_jobs` table in SQLite.
   - Jobs must be idempotent: mark sent-at rows so a restart doesn't double-send.
   - "Skip the email if already read" is a query at send time, not a cancellation API.
   - Digests are a `GROUP BY recipient` query over unsent rows in a window.
   - Per ADR 0006, this design rules out more than one instance, and so does the app as a whole already.
7. **Retention.** A periodic delete of old In-app Notifications. This is the map's open "Retention" question.

Roughly, a home build owns the scheduler, idempotency, unsubscribe compliance and the feed UI. A vendor owns those but adds a second store of record, a network dependency, a socket client and a monthly bill once volume passes the free tier.
